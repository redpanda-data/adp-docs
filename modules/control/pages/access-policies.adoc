Access policies give you fine-grained, attribute-based access control (ABAC) on top of roles: permit or forbid specific actions for specific people, groups, or resources, with conditions that read resource tags and ownership. Use them to express rules that roles can't, such as denying a group access to production-tagged agents or letting only a resource's creator modify it.

== How access policies work

Access policies use the https://www.cedarpolicy.com/[Cedar policy language^]. A policy is a `permit` or `forbid` statement over three parts:

* *Principal*: Who the policy applies to. A user (`User::"alice@example.com"`) or a group (`Group::"support"`). Principals don't carry attributes such as department or nationality: model those facts as group membership.
* *Action*: What operation the policy covers. An action ID is an entity type and a verb joined by a dot, for example `Action::"Agent.get"` or `Action::"McpServerTool.call"`. The entity rides inside the action ID, so an action always names the one resource type it applies to. See <<action-reference,Action reference>>.
* *Resource*: What the action targets, as a typed entity, for example `resource is Agent` for every agent or `resource == Agent::"support-bot"` for one.

[IMPORTANT]
====
Access policies use a different action vocabulary from RBAC. The `dataplane_adp_*` permission strings that roles bundle still gate the API and still appear in xref:control:permissions-reference.adoc[], but they are *not* policy actions. A policy that names one fails validation with an unrecognized-action error.
====

Access policies compose with role-based access control (RBAC) rather than replacing it:

* Every request is denied unless a `permit` matches it.
* Your existing role bindings count as permits. Redpanda derives them for you, so roles keep working unchanged and you never author them by hand.
* A matching `forbid` always wins, including over the access a role grants. This is what makes cross-cutting denials possible: one `forbid` can override any number of grants.

Enforcement is fail-closed. A `forbid` that errors during evaluation denies the request rather than being skipped, and enforcement continues from the last delivered policy set if policy distribution is interrupted.

== Action reference

Verbs are shared across entity types, and an action ID pairs one verb with one entity. The following table lists the verbs each entity type supports. Combine them with a dot to get the action ID: `Budget` plus `update` is `Action::"Budget.update"`.

[cols="1,3"]
|===
|Entity type |Verbs

|`Agent`
|`get`, `list`, `create`, `update`, `delete`, `invoke`

|`AgentCredential`
|`list`, `create`, `delete`

|`AgentTrigger`
|`get`, `list`, `create`, `update`, `delete`

|`Session`
|`get`, `list`, `delete`

|`Transcript`
|`get`, `list`

|`McpServer`
|`get`, `list`, `create`, `update`, `delete`, `initialize`, `ping`, `tools_list`, `prompts_get`, `prompts_list`, `resources_list`, `resources_read`, `resources_templates_list`, `logging_set_level`

|`McpServerTool`
|`call`

|`LLMProvider`
|`get`, `list`, `create`, `update`, `delete`, `invoke`

|`Model`
|`get`, `list`

|`Guardrail`
|`get`, `list`, `create`, `update`, `delete`

|`Budget`
|`get`, `list`, `create`, `update`, `delete`

|`Spending`
|`get`

|`OAuthProvider`
|`get`, `list`, `create`, `update`, `delete`, `attach`

|`OAuthClient`
|`get`, `list`, `create`, `update`, `delete`

|`OAuthConnection`
|`get`, `list`, `authorize`, `revoke`

|`AdminConnection`
|`list`, `revoke`, `rotate`

|`Policy`
|`get`, `list`, `create`, `update`, `delete`

|`PolicyTemplate`
|`get`, `list`, `create`, `update`, `delete`

|`EffectivePolicySet`
|`get`, `list`
|===

Each verb also exists as an action group, so `action in Action::"get"` matches every `<Entity>.get` action. Groups are shorthand, and they come with one rule.

[IMPORTANT]
====
A `permit` that references an action group must pin the resource type, with `resource is Agent` or `resource == Agent::"support-bot"`. Saving an unpinned group permit fails, because group membership grows as new resource types adopt the verb, so the stored grant would silently widen on the next deployment. `forbid` statements are exempt: a growing deny widens in the safe direction.

To grant a verb across the whole data plane, name each `<Entity>.<verb>` action explicitly. The Access page does this for you when you pick verbs with the *All resources* scope.
====

== Prerequisites

* Access policies enabled for your organization.
* Permission to author policies: the `dataplane_adp_policy_*` permissions. The built-in Admin and Writer roles carry them, and Reader can view policies but not change them. See xref:control:permissions-reference.adoc[].

== Open the Access page

Open *Access* in the sidebar. Two tabs cover everyday work:

* *Policies*: The access policies you author. This is where you create, edit, and delete them.
* *Templates*: Reusable policy templates, including the built-in quick-start set.

The *Roles* tab shows the roles defined for your organization as bundles of actions, and a *System policies* tab gives highly privileged users a read-only audit view of the permits derived from role bindings. Neither is something you author.

== Create a policy

. On the *Policies* tab, click *Create policy*.
. Give the policy a *Name*.
. Choose the *Effect*: *Permit* grants access that roles don't, and *Forbid* takes access away no matter what roles grant.
. Set the *Principal*: a user from your organization directory, or a group name from your identity provider. Group membership stays managed in the IdP.
. Under *Permissions*, choose how to grant:
** *Actions* picks individual verbs by hand for a one-off grant.
** *Template* links to a reusable template. A template carries a fixed, permit-only action set, and the policy's own effect and conditions don't apply.
. In *Actions* mode, work through the three steps:
.. *Action*: Select verbs. They're grouped as Management (`get`, `list`, `create`, `update`, `delete`), Execution (`invoke`, `call`), Access lifecycle (`attach`, `authorize`, `revoke`, `rotate`), and MCP protocol.
.. *Applies to*: Choose *All resources* for the whole data plane, *All of a type* for every resource of one type, or *Specific resource* for one. Picking a child type under *Specific resource* scopes to the children of one parent, such as the tools of one MCP server.
.. *Conditions*: Optional. Add *WHEN* rows to narrow when the policy applies and *UNLESS* rows to carve out exceptions. Each row conditions on a resource tag, its creator, or its creation time.
. Click *Create policy*.

The picker only offers verbs the scoped type supports, and narrowing the scope drops any selected verb the new type doesn't have. The footer summarizes the grant in plain language and lists whatever is still missing before you can save.

A `permit` that covers write verbs across the whole data plane triggers a warning. Narrow the scope instead.

Every save validates the policy against the current schema. The save fails with a specific error if the policy references an unknown action or entity type, reads an attribute that doesn't exist, or uses an unsafe condition, so a policy that stores successfully is well-formed.

The *Form* and *Cedar* toggle at the top of the page switches between the form fields and the Cedar text, in sync both ways. Writing Cedar directly produces the same policy. The toggle doesn't appear when your starting point fixes the principal or the scope, such as an agent's *Permissions* tab, because raw Cedar could rewrite the locked clause.

Some older policies grant a whole role bundle instead of a set of verbs. You can open one to see what it grants, but not edit it here.

=== Start from a template

The *Templates* tab includes four built-in quick-start templates, each a superset of the one before it:

[cols="1,3"]
|===
|Template |Grants

|Read only
|View-only access across all resources (get, list, and read).

|Sandboxed
|Read-only access plus the ability to use agents and MCP servers (invoke, call tools). No management.

|Standard
|Sandboxed access plus full management of agents, MCP servers, LLM providers, guardrails, triggers, and budgets. Excludes managing access policies.

|Full access
|Every Agent Data Plane action, including managing access policies.
|===

Templates are permit-only, so a policy that links one grants access and never denies it. Later edits to the template apply to every policy linked to it.

A built-in *Owner lifecycle* policy also ships with the feature: users can get, update, and delete the agents, MCP servers, LLM providers, guardrails, and budgets they created, plus create and manage triggers on their own agents. It doesn't cover creating top-level resources, because a create authorizes against a payload that has no creator recorded yet, and it doesn't cover agent credentials or sessions, which record no creator at all.

== Write conditions

Conditions make policies attribute-based: they read resource tags, group membership, and ownership at evaluation time. Follow these rules to write conditions that behave the way you expect. Validation at save time enforces most of them.

=== Guard every tag read

Reading a tag a resource doesn't have is an evaluation error, not false. Always pair `getTag` with a `hasTag` check on the same key:

[source,cedar]
----
forbid (
  principal,
  action == Action::"Agent.get",
  resource is Agent
) when {
  resource.hasTag("itar") &&
  resource.getTag("itar") == "true" &&
  !(principal in Group::"us-persons")
};
----

Without the `hasTag` guard, the policy errors on every untagged resource, and an erroring `forbid` denies. You would block access to every untagged agent, the opposite of the intent. Validation rejects the unguarded form when you save.

Only `Agent` and `Policy` resources carry tags. A tag condition on any other type is dead code: it's valid Cedar but can never match, and validation flags it when the policy pins the resource type. Pin the type on every policy that reads tags so you get that check.

=== Model people facts as groups

Principals carry an email and group memberships, nothing else. Write `principal in Group::"nationality/US"`, not `principal.nationality == "US"`. Validation rejects attribute reads on principals.

=== Guard ownership reads

To reference a resource's creator, guard the read the same way as a tag:

[source,cedar]
----
resource has created_by && resource.created_by == principal
----

Write the attribute on the left of the comparison. The condition builder on the Access page parses this shape back into editable rows, and `principal == resource.created_by` leaves the policy read-only in the UI.

=== Conditions on writes evaluate the resulting state

On create and update actions, `resource` is the state the operation produces, not the stored row. A `forbid` on production-tagged agents therefore fires on any update to an agent that carries the tag, even an update that doesn't touch tags, and stops firing on the update that removes the tag. That makes a write-scoped tag condition a state invariant, not a request check, so a violating resource is frozen for non-exempt principals until an update fixes the violation. Deleting always works, because delete evaluates the stored row.

To gate the transition itself (adding or removing a specific tag), condition on `changed_tags`, the set of tag keys the update adds, removes, or changes:

[source,cedar]
----
forbid (
  principal,
  action == Action::"Agent.update",
  resource is Agent
) when {
  resource has changed_tags &&
  resource.changed_tags.contains("itar") &&
  !(principal in Group::"itar-cleared")
};
----

`changed_tags` exists only on the update path, so this policy doesn't fire on create. `Agent` is the only entity type that carries it. To close the create case too, pair the policy with a create-scoped clause that reads the tag directly:

[source,cedar]
----
forbid (
  principal,
  action == Action::"Agent.create",
  resource is Agent
) when {
  resource.hasTag("itar") &&
  !(principal in Group::"itar-cleared")
};
----

=== Guard optional scalar attributes too

A scalar field that holds its zero value doesn't appear on the entity at all, so `resource.enabled == true` errors whenever `enabled` is `false`, and that error denies. Guard scalar reads the same way as tags: `resource has enabled && resource.enabled == true`.

== Manage an agent's permissions

Each agent's detail page includes a *Permissions* tab with two cards:

* *Roles & access* lists the RBAC role bindings that apply to the agent, both bound directly to it and inherited from the data-plane scope. It's read-only here, because those bindings are managed in the control plane.
* *Access policies* lists what the agent itself may do, acting as its own principal. *Create policy* opens the same policy form with the principal locked to the agent's service account, so the policy targets a `User` principal like any other.

An MCP server's *Access* tab works the same way, with the scope locked to that server.

== Manage policies from the CLI

Run `rpk ai policy` commands to create, get, list, update, and delete access policies, and to apply or diff them from manifest files for GitOps workflows. See xref:reference:rpk/rpk-ai/rpk-ai-policy.adoc[].

== Examples

These policies cover the shapes that come up most often. Adapt the group names, tag keys, and actions to your environment.

=== Deny a group access to production agents

Members of `contractors` can't read agents tagged `env=prod`, no matter what their roles grant:

[source,cedar]
----
forbid (
  principal in Group::"contractors",
  action == Action::"Agent.get",
  resource is Agent
) when {
  resource.hasTag("env") &&
  resource.getTag("env") == "prod"
};
----

=== Only owners can modify their agents

Nobody but an agent's creator can update it:

[source,cedar]
----
forbid (
  principal,
  action == Action::"Agent.update",
  resource is Agent
) unless {
  resource has created_by && resource.created_by == principal
};
----

=== Default-closed classification gate

Nothing is readable until it's explicitly cleared. An agent with no `classification` tag is denied, and only `classification=public` clears the gate:

[source,cedar]
----
forbid (
  principal,
  action == Action::"Agent.get",
  resource is Agent
) unless {
  resource.hasTag("classification") &&
  resource.getTag("classification") == "public"
};
----

== Troubleshoot

=== A policy won't save

Validation runs in strict mode against the current schema and reports every problem it finds. The most common ones:

[cols="2,3"]
|===
|Error |Fix

|Unrecognized action
|Use an `<Entity>.<verb>` action ID from <<action-reference,Action reference>>. RBAC permission strings such as `dataplane_adp_agent_get` are not access-policy actions.

|Unrecognized entity type
|Check the spelling. A resource that exists in the API isn't automatically a policy entity type.

|Can't guarantee the safety of a tag access
|Add `resource.hasTag("<key>") &&` immediately before the `getTag` call, on the same key.

|Attribute not found on entity type `User`
|Principals carry no attributes. Model the fact as a group and write `principal in Group::"…"`.

|Permit references an action group without a resource type pin
|Add `resource is <Entity>`, or name each `<Entity>.<verb>` action explicitly.

|Clause can never match
|The condition targets something that doesn't exist on the pinned type, such as a tag condition on a type that carries no tags. Retarget the policy or drop the clause.
|===

Validation applies to new writes only. Validation never rejects a policy stored before a schema change, so re-save an older policy (even a no-op edit) to run the current checks against it.

=== A request is denied

A denial caused by access policies surfaces as a permission-denied error:

* A `forbid` that matches cleanly returns a generic permission-denied message. Check the *Policies* tab for a `forbid` covering the action and resource.
* A `forbid` that errors during evaluation also denies, and the error names the policy. Check that policy for an unguarded tag or attribute read, then re-save it to run current validation against it.
* A missing `permit` also denies, with the same generic message. Confirm the principal holds a role that covers the action, or add a `permit` policy for it.

On the payload-gated update actions, authorization runs inside the write transaction, so an unauthorized caller can receive an invalid-argument or not-found error before the permission-denied one. Don't write clients that assume a deny always comes first.
